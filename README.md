# GameTrace

**Build protocol-aware debugging workflows through plugins**

Capture traffic on a probe → decode it with a plugin → inspect requests, state changes and behavior.
The whole loop is exposed as MCP tools, so an AI agent can drive it — with a Web dashboard for humans.

GameTrace is the pipeline, not a protocol encyclopedia. It does **not** try to understand every game
protocol out of the box — protocol knowledge lives in **plugins**: one Go binary plus one
`plugin.yaml` per protocol. GameTrace owns capture, dispatch, storage and query; a plugin decides what
a byte range means. No plugin for your protocol yet? Let your agent scaffold one **in your own
workspace** (`scaffold_plugin` returns template file contents — GameTrace never stores plugin source,
never compiles and never launches it; you build and run the plugin on your machine, then `connect_plugin`
tells the platform to look for it in the registry), or point the pipeline at a decoder you already
have — that is the extension point the whole design is built around.

Raw traffic is captured live on a team member's or a remote **probe's** machine (or replayed from
`.pcap`), decoded by independent plugin processes, and assembled into a **debug trace** —
request/response pairs, state changes, and causal chains (OpenTelemetry-style `TraceContext`). Humans
reflect on the same data through a first-class Web dashboard (`web/`) that surfaces sessions,
connections, protocol events, pair relationships, and entity
state-change diffs.

## Features

- **🖥️ Web dashboard** — a first-class UI (`web/`)：三个空间按 URL 深度分层（工作台 → 项目 → 会话），会话里是 概览 / 连接 / 协议事件 / 状态变更 / 原始包 五个视图，连同项目一键抓包、设备与探针接入、成员与代理配置。
- **📡 Live capture & replay (local & probes)** — per-port pcap capture or offline `.pcap` replay; capture locally or push to a remote **探针 (probe)** machine (`gt-agent`); concurrent sessions with per-project plugin binding and data persisted to disk by default.
- **🧩 Hot-swappable decoder plugins** — every plugin is an independent process over gRPC: hot-load, hot-swap on a *running* session (`set_session_plugin`), crash-isolated from the pipeline.
- **🧭 Debug trace (pairing & state diffs)** — every decoded event carries an OpenTelemetry-style `TraceContext` (causation = parent, correlation = conversation); 协议事件 puts a pair badge on a row whose request/response partner is known, and expanding it shows 左请求 / 右响应 side by side (the partner is fetched by `causation_id` when it is off the current page). 状态变更 projects field-level before/after (e.g. `Player:1001.hp: 100 → 65`) via `query_state_changes` / `get_state_change_detail`. A first-class session-timeline view is on the Roadmap.
- **🤖 Agent-driven plugin development** — `scaffold_plugin` (returns file contents, writes nothing) → you build + run the plugin locally → `connect_plugin` → `verify_plugin`, with automated failure attribution (`explain_plugin`); the contract and dev guide are served to agents via `get_plugin_contract` / `get_plugin_dev_guide`.
- **🔒 Your source stays yours** — plugin source, binary and process all live on your machine. The platform has no plugin directory: it only observes instances that register themselves, and keeps verification evidence in its own database.

## Quick Start

Pick the track that matches what you are.

### A. 我是 QA / 测试：抓一次包，把问题定位到协议字段（5 步）

> **前提**：服务器已由管理员部署好（[团队部署指南](docs/team-deployment.md)）。
> 在**要抓包的那台机器**上装好抓包驱动：Windows 装 [Npcap](https://npcap.com/)
> （勾选 "WinPcap API-compatible Mode"）· Linux 装 `sudo apt install libpcap-dev`。

1. **登录服务器** — 浏览器打开 `http://<服务器>:<GT_MCP_PORT>`（compose 默认宿主端口 `18781`，
   容器内为 `8781`）。用管理员给你的 token 登录；没有令牌就点
   「没有令牌？快速开始」自助注册，立刻拿到自己的身份。

2. **下载 gt-agent，接入这台机器** — 点顶部工具栏「接入设备」→ 选目标操作系统 →「下载探针」，
   在**要抓包的那台电脑**上解压并运行 gt-agent（无需填任何参数）：

   - **Windows**：解压 zip 双击 `gt-agent.exe`（需先装 [Npcap](https://npcap.com/)，勾选 "WinPcap API-compatible Mode"）；
   - **Linux / macOS**：`unzip gt-agent-linux-amd64.zip && ./gt-agent`

   缺少的平台产物可直接在下载页点「现场编译」由服务器即时生成（同一平台的产物全局
   复用，已有则无需重新编译；macOS 产物由镜像构建期预置）。

   zip 已内置回连地址与凭证（`config.embedded.json`），探针启动即注册到你的团队。
   **全程不用手填 token、回连地址或会话 ID。**

3. **选择游戏端口** — 设备在「我的设备」显示在线后，点顶部「开始抓包」：选刚接入的机器 →
   填游戏端口（如 `9250`）→ 选解码插件 → 开始。
   （探针只负责接入这台机器；端口与插件是在「开始抓包」时才指定的。）

4. **开始抓包并复现问题** — 正常操作游戏客户端，让流量跑起来。
   想换端口或换插件不用重新接入，再点一次「开始抓包」即可。

5. **查看协议行为** — 点「停止抓包」，进入该会话的「协议事件」视图：

   - 每一行是一条解码后的协议消息（msg_name / 方向 / 语义标签 / 字段摘要），带配对角标的行点开就是
     左请求 / 右响应的一问一答；
   - 「状态变更」— 按**操作 / 实体 / 时间**三个视角看字段的前后值（如 `Player:1001.hp: 100 → 65`）。

> 看不到数据？先查 [成员上手指南 · 常见问题](docs/member-onboarding.md#4-常见问题)
> （端口是否一致、防火墙是否放行 `9091/9092`、Npcap/libpcap 是否装好）。

### B. 我是开发者：从源码跑起来

**Prereqs:** Go 1.26+ · libpcap (Linux) / [Npcap](https://npcap.com/) (Windows)

```bash
make build        # gt-mcp + gt-pipeline + gt-singbox-agent → bin/

# terminal 1 — runtime plane (data path; start first)
./bin/gt-pipeline.exe -workdir . -log-format text

# terminal 2 — control plane
./bin/gt-mcp.exe -work-dir . -log-format text

# terminal 3 — probe on this machine (pipeline no longer captures locally;
# all raw frames arrive via agent ingest :9092)
go run ./cmd/gt-agent
```

Point your AI agent at `http://127.0.0.1:8781/mcp` (Streamable HTTP) or `http://127.0.0.1:8781/sse` (SSE), then have it smoke-test the stack:

```
start_capture(port=8984)      # session starts; keep the session_id
#   … generate traffic: go run ./examples/http/server   (+ ./examples/http/client)
get_session_status            # packets_in > 0 · decode_errors == 0
list_decoded_data(limit=50)   # decoded events — needs a decoder plugin, see below
```

`make test` runs the test suite; `make run-mcp` / `make run-pipeline` use `go run` for fast iteration.

Want generated data instead of real traffic? `go test ./cmd/gt-pipeline/ -run TestSimulate` spins up an
in-process pipeline with a synthetic probe + decoder (69 frames → 83 state changes across 5 entities);
`SIM_SERVE=1` additionally serves the Web UI on `http://127.0.0.1:8781/`.

## Architecture

Two planes, split so **MCP stays a pure adapter** — `gt-mcp` spawns no subprocesses, writes no files, does no failure attribution; it only forwards. Plugin *source, build and process* are not a plane at all: they live on the user's machine, and the platform only observes instances that register themselves.

```
Team member host                    AI Agent (Claude / DeepSeek / …)
┌────────────────────────────────┐      │  MCP over HTTP — :8781  (/sse + /message · /mcp)
│  gt-agent                     │      │  Authorization: Bearer <token>
│  ├─ capture ingest ──┼── :9092 ─┐     ▼
│  └─ plugin tunnel ───┼── :9091 ─┼─────────────────────────────────────┐
│                       │         │      Runtime Plane — gt-pipeline    │
│  decoder plugin       │         │      capture → decode → project     │
│  source / binary /    │         │      → SQLite · PluginRegistry      │
│  process (yours)      │         │      :9091 · AgentIngest :9092      │
└───────────────────────┼─────────┘      · MCP adapter gt-mcp :8781     │
                        └──── gRPC register + heartbeat ───────────────┘
                              (observed, never managed)
```

| Port | What listens |
|------|--------------|
| `:8781` | gt-mcp HTTP — `/sse` + `/message` (SSE) · `/mcp` (Streamable HTTP) · `/events/plugins` — Bearer-auth when `GT_AUTH_TOKENS` is set |
| `:9888` | CaptureControl gRPC — gt-mcp → gt-pipeline |
| `:9091` | PluginRegistry gRPC — decoder plugins → gt-pipeline (remote members register through the gt-agent tunnel) |
| `:9092` | AgentIngest gRPC — gt-agent pushes raw frames from a team member's machine |

## Team Deployment

Run a shared server for your team with Docker Compose — three services (gt-pipeline + gt-mcp + postgres). Fill the five required variables in `.env` first (`GT_AUTH_TOKENS=alice=gt_xxx,bob=gt_yyy` with an `:admin` suffix for admins, `GT_PUBLIC_HOST`, `GT_PUBLIC_REGISTRY_PORT`, `GT_PUBLIC_INGEST_PORT`, `GT_LAN_IP`), then:

```bash
cp .env.example .env   # 填好上述 5 个必填项（compose 用 ${VAR:?} 强制校验）
docker compose up -d --build
```

Host-published ports default to **`19888/19091/19092/18781`** (container-internal ports keep the `9888/9091/9092/8781` numbering; see the offset note at the top of `docker-compose.yml`).

Members connect from their own machines with a single `gt-agent` binary that pushes captures to `:9092` and hosts local decoder plugins via the registry tunnel (`GT_TUNNEL=1` is injected for them). Full walkthroughs: [团队部署指南](docs/team-deployment.md) · [成员上手指南](docs/member-onboarding.md).

## Plugin SDK

Plugins depend only on [`github.com/OwnSecurityGuard/gametrace/sdk`](sdk/) — an independent Go module that lives in this monorepo under `sdk/`, zero coupling to gametrace internals. A plugin is **one Go binary + one `plugin.yaml` manifest**:

- the manifest declares the plugin's identity and contract — `api_version`, `protocol`, `transports`, and `semantic_rules` ([sdk/examples/http-stream-decoder/plugin.yaml](sdk/examples/http-stream-decoder/plugin.yaml) is a complete example)
- the host validates that contract at registration *and* per event at decode time
- you launch the binary yourself, pointing it at the advertised registry address (`get_registry_addr` / `get_plugin_env`) — the platform never launches it for you

The lifecycle is fully agent-drivable, with failure attribution built in:

```
scaffold_plugin ──► build + run locally ──► connect_plugin ──► verify_plugin
                        │                        │                  │
                        └───────────── explain_plugin ──────────────┘
                        (attributes the most recent connect / verify failure)
```

Human-readable guide: [`docs/gt-plugin-development.md`](docs/gt-plugin-development.md).

