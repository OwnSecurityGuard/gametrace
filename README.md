# GameTrace

**Build protocol-aware debugging workflows through plugins**

Capture traffic on a probe → decode it with a plugin → inspect requests, state changes and behavior.
The whole loop is exposed as MCP tools, so an AI agent can drive it — with a Web dashboard for humans.

GameTrace is the pipeline, not a protocol encyclopedia. It does **not** try to understand every game
protocol out of the box — protocol knowledge lives in **plugins**: one Go binary plus one
`plugin.yaml` per protocol. GameTrace owns capture, dispatch, storage and query; a plugin decides what
a byte range means. No plugin for your protocol yet? Let your agent scaffold one
(`create_plugin` → `build_plugin` → `verify_plugin`), or point the pipeline at a decoder you already
have — that is the extension point the whole design is built around.

Raw traffic is captured live on a team member's or a remote **probe's** machine (or replayed from
`.pcap`), decoded by independent plugin processes, and assembled into a **debug trace** —
request/response pairs, state changes, and causal chains (OpenTelemetry-style `TraceContext`). Humans
reflect on the same data through a first-class Web dashboard (`web/`) that surfaces sessions,
connections, protocol events, extract parent/child hierarchies, pair relationships, and entity
state-change diffs.

## Features

- **🖥️ Web dashboard** — a first-class UI (`web/`): 我的抓包 / 会话概览 / 连接 / 协议数据（事件 · 关系 · 状态变更）/ 行为 / 插件 / 原始包，连同项目一键抓包、设备与探针接入、成员与代理配置。
- **📡 Live capture & replay (local & probes)** — per-port pcap capture or offline `.pcap` replay; capture locally or push to a remote **探针 (probe)** machine (`gt-agent`); concurrent sessions with per-project plugin binding and data persisted to disk by default.
- **🧩 Hot-swappable decoder plugins** — every plugin is an independent process over gRPC: hot-load, hot-swap on a *running* session (`set_session_plugin`), crash-isolated from the pipeline.
- **🧭 Session timeline (debug trace)** — `get_session_timeline` builds the full request/response tree for a capture session from `TraceContext` (causation = parent, correlation = conversation). This is the **"capture once, see the whole flow"** MVP view. `trace_protocol_flow` drills into one behavior's chronological causation chain.
- **🤖 Agent-driven plugin development** — `create_plugin` → `build_plugin` → `activate_plugin` → `verify_plugin` with automated failure attribution (`explain_plugin`); the contract and dev guide are served to agents via `get_plugin_contract` / `get_plugin_dev_guide`.
- **🎯 Behavior windows** — mark a user operation (`begin_capture_run` … `end_capture_run`) and get its chronological causation chain (`trace_protocol_flow`).
- **🔒 Physical dev/prod isolation** — all plugin-dev powers live in an optional Developer Plane; production just never starts that process. Not a feature flag — a missing process.

## Quick Start

Pick the track that matches what you are.

### A. 我是 QA / 测试：抓一次包，把问题定位到协议字段（5 步）

> **前提**：服务器已由管理员部署好（[团队部署指南](docs/team-deployment.md)）。
> 在**要抓包的那台机器**上装好抓包驱动：Windows 装 [Npcap](https://npcap.com/)
> （勾选 "WinPcap API-compatible Mode"）· Linux 装 `sudo apt install libpcap-dev`。

1. **登录服务器** — 浏览器打开 `http://<服务器>:8781`。用管理员给你的 token 登录；没有令牌就点
   「没有令牌？快速开始」自助注册，立刻拿到自己的身份。

2. **下载 gt-agent，接入这台机器** — 点顶部工具栏「接入设备」→「我的接入」，选操作系统 →
   「生成启动码」→ 复制命令，在**要抓包的那台电脑**执行：

   - **Windows**：在 **PowerShell** 粘贴执行；
   - **Linux / macOS**：`curl -fsSL "<服务器>/setup.sh?code=GT-XXXX-XXXX&platform=linux/amd64" | bash`

   脚本会自动：领取配置（token / 回连地址）→ 下载对应平台的 gt-agent → 写入配置 → 启动并注册成探针。
   **全程不用手填 token、回连地址或会话 ID。** 启动码**一次性 + 24 小时有效**，过期重新生成即可。

3. **选择游戏端口** — 设备在「我的设备」显示在线后，点顶部「开始抓包」：选刚接入的机器 →
   填游戏端口（如 `9250`）→ 选解码插件 → 开始。
   （启动码只负责接入这台机器；端口与插件是在「开始抓包」时才指定的。）

4. **开始抓包并复现问题** — 正常操作游戏客户端，让流量跑起来。
   想换端口或换插件不用重新接入，再点一次「开始抓包」即可。

5. **查看协议行为** — 点「停止抓包」，去「协议数据」：

   - `事件` — 解码后的每一条协议消息（含 msg_name / 方向 / 字段）；
   - `关系` — 请求/响应配对与父子层级；
   - `状态变更` — 按**操作 / 实体 / 时间**三个视角看字段的前后值（如 `Player:1001.hp: 100 → 65`）。

   想看"某一次操作到底触发了哪些包"，用「行为」：标记一个行为窗口
   （`begin_capture_run` … `end_capture_run`）后看它的因果链。

> 看不到数据？先查 [成员上手指南 · 常见问题](docs/member-onboarding.md#4-常见问题)
> （端口是否一致、防火墙是否放行 `9091/9092`、Npcap/libpcap 是否装好）。

### B. 我是开发者：从源码跑起来

**Prereqs:** Go 1.25+ · libpcap (Linux) / [Npcap](https://npcap.com/) (Windows)

```bash
make build        # gt-mcp + gt-pipeline + gt-plugin-dev → bin/

# terminal 1 — runtime plane (data path; start first)
./bin/gt-pipeline.exe -workdir . -log-format text

# terminal 2 — control plane (embeds the Developer Plane)
./bin/gt-mcp.exe -work-dir . -plugins-dir plugins -log-format text
```

Point your AI agent at `http://127.0.0.1:8781/mcp` (Streamable HTTP) or `http://127.0.0.1:8781/sse` (SSE), then have it smoke-test the stack:

```
start_capture(port=8984)      # session starts; keep the session_id
#   … generate traffic: go run ./examples/http/server   (+ ./examples/http/client)
get_session_status            # packets_in > 0 · decode_errors == 0
list_decoded_data(limit=50)   # decoded events — needs a decoder plugin, see below
```

`make test` runs the test suite; `make run-mcp` / `make run-pipeline` use `go run` for fast iteration.

Want generated data instead of real traffic? `go test ./cmd/gt-pipeline/ -run TestSimulate` spins up an
in-process pipeline with a synthetic probe + decoder (69 frames → 83 state changes across 5 entities);
`SIM_SERVE=1` additionally serves the Web UI on `http://127.0.0.1:8781/`.

## Architecture

Three planes, split so **MCP stays a pure adapter** — `gt-mcp` spawns no subprocesses, writes no files, does no failure attribution; it only forwards. Filesystem and process powers live one plane down, so a production deployment that never starts the Developer Plane has *zero* dev-capability exposure.

```
Team member host                    AI Agent (Claude / DeepSeek / …)
┌──────────────────────┐                  │  MCP over HTTP — :8781  (/sse + /message · /mcp)
│  gt-agent           │                  │  Authorization: Bearer <token>
│  ├─ capture ingest ──┼── :9092 ──┐      ▼
│  └─ plugin tunnel ───┼── :9091 ─┐┌─────────────────────────────────────────────┐
└──────────────────────┘          ││  gt-mcp (:8781) — pure adapter: zero exec  │
                                  ││  Bearer auth via GT_AUTH_TOKENS            │
┌─────────────────────────────────▼─────────┬───┴─────────────────────────────┐
│  Developer Plane                          │  Runtime Plane — gt-pipeline   │
│  gt-plugin-dev                           │  capture → decode → project     │
│  scaffold / build /                       │  → SQLite · PluginRegistry      │
│  activate / explain                       │  :9091 · AgentIngest :9092      │
│  (prod: never started)                    └───────────────┬─────────────────┘
└──────┼────────────────────────────────────────────────────┤ gRPC register + heartbeat
       │ launch binary, inject                              │ (observed, never managed)
       │ GT_REGISTRY_ADDR                                  ▼
       └──────────►  decoder plugin processes ◄────────────┘
```

| Port | What listens |
|------|--------------|
| `:8781` | gt-mcp HTTP — `/sse` + `/message` (SSE) · `/mcp` (Streamable HTTP) · `/events/plugins` — Bearer-auth when `GT_AUTH_TOKENS` is set |
| `:9888` | CaptureControl gRPC — gt-mcp → gt-pipeline |
| `:9091` | PluginRegistry gRPC — decoder plugins → gt-pipeline (remote members register through the gt-agent tunnel) |
| `:9092` | AgentIngest gRPC — gt-agent pushes raw frames from a team member's machine |
| `:8089` | PluginDev gRPC — only when the Developer Plane runs standalone (default: embedded at `127.0.0.1:0`) |

## Team Deployment

Run a shared server for your team with Docker Compose (gt-pipeline + gt-mcp, ports `9888/9091/9092/8781`, per-member tokens via `GT_AUTH_TOKENS=alice=gt_xxx,bob=gt_yyy`, `:admin` suffix for admins):

```bash
cp .env.example .env && docker compose up -d --build
```

Members connect from their own machines with a single `gt-agent` binary that pushes captures to `:9092` and hosts local decoder plugins via the registry tunnel (`GT_TUNNEL=1` is injected for them). Full walkthroughs: [团队部署指南](docs/team-deployment.md) · [成员上手指南](docs/member-onboarding.md).

## Plugin SDK

Plugins depend only on [gt-plugin-sdk](https://github.com/OwnSecurityGuard/gt-plugin-sdk) — a separate repo, zero coupling to gametrace internals. A plugin is **one Go binary + one `plugin.yaml` manifest**:

- the manifest declares the contract — capabilities, schemas, and state subjects (`plugins/godot-gateway/plugin.yaml` is a complete example)
- the host validates that contract at registration *and* per event at decode time
- `activate_plugin` launches the binary and injects `GT_REGISTRY_ADDR` for you

The lifecycle is fully agent-drivable, with failure attribution built in:

```
create_plugin ──► build_plugin ──► activate_plugin ──► verify_plugin
                     │                 │                   │
                     └────────── explain_plugin ────────────┘
                     (attributes the most recent build / activate / verify failure)
```

Human-readable guide: [`docs/gt-plugin-development.md`](docs/gt-plugin-development.md).
